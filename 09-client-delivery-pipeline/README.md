# 09 · Client Delivery Pipeline — Client Delivery Pack

**For the owner:** take one client job from brief to approved report without invented prices, unapproved
go-lives or reports that say "all checks passed" when they did not. The AI prepares and checks; a named person
makes four recorded decisions. The pack also covers the business edges: service boundary and a pricing method.

**Shown in:** Episode 9, "What we are building: one job on a conveyor", "Brief → unknowns → proposal → GATE 1",
"Isolated build → review → GATE 2", "Site Watch → preview → GATE 3 → report → GATE 4", "Test 1: the vague brief",
"Test 2, quick: going live without approval", "Test 3: the report that said "all checks passed"",
"What is in the service, and what is not", "The pricing method".

**Prerequisites:** the earlier modules installed (`kiran-core` plugin from module 07, Site Watch from module 04,
the capped-run pattern from module 06), Python 3.11+, git, and a GitHub repository for the go-live workflow
(the go-live gate needs a GitHub plan that supports required reviewers on your repository type). An API key is
optional: with one, per-client costs come from your Console bill instead of a list-price estimate.

All clients, data and prices are fictional test data (Kiran Studio, Sufi Threads). No price figures anywhere.

## Use it in 5 steps

1. **Check prerequisites.** `python --version` (3.11+), `git --version`, `claude --version`. Make this folder a git
   repository with one commit (`git init`, `git add -A`, `git commit -m start`): the pipeline commits each gate.
   Install `kiran-core` from module 07 for this project. `pipeline.py` runs Claude Code with `CLAUDE_CONFIG_DIR=.cfg`,
   so install it there too. If the relative marketplace path in `.claude/settings.json` does not resolve on your
   machine, replace it with the full path to `07-agency-kit-plugins/kiran-marketplace`.
2. **Try the offline parts (no model call):**
   `python build_report.py fixtures/sample-runs/sufi-winter --out out/report.md` and
   `python build_report.py fixtures/test-setups/b4-planted-rejected-finding --check fixtures/test-setups/b4-planted-rejected-finding/handcrafted.summary.md`
   (exit 1: "passed" where the counts disagree).
3. **Start a job:** copy `jobs/_new-job-template/` to `jobs/<your-job>/`, paste the brief, add your job and client
   to `CLIENT` in `pipeline.py`, then `python pipeline.py proposal --job <your-job>`. Fill the price in
   `proposal.md` yourself, send it by hand, and record Gate 1:
   `python pipeline.py approve send --job <your-job> --by "<name>" --role Owner`.
4. **Answers, build, QA:** `python pipeline.py answers --job <your-job> --reply <reply.json>` → `build` (refuses while
   an unknown is open) → `approve merge` after reading the diff → `qa` → `approve go-live` after one test enquiry by
   hand. Live release runs in GitHub through `go-live.yml`. Read `GATE-SHEET.md` before each approval.
   Windows note: set `PYTHONIOENCODING=utf-8` if the console shows encoding errors. The Episode 8 policy test runs
   in WSL (`EP8_WSL_DISTRO=<distro>`); without the Episode 8 lab, add `--skip-policy` to `build` and say so.
5. **Report and price:** `python pipeline.py report --job <your-job>` → `approve report` (refused if the report
   says "passed" where the counts disagree) → `python pipeline.py summary --job <your-job>` for
   `runs/<job>/cost-report.txt`. Put that total in row 1 of `pricing-worksheet.md`, time your gates for row 2,
   fill `SERVICE-BOUNDARY.md`, and decide project or retainer with `PROJECT-VS-RETAINER.md`.

## Limits — what it does NOT do

- It was run end to end once, on one fictional client with test data, with a stand-in owner at the gates. Gate
  minutes from that run are machine pace, not human pace.
- The GitHub half of go-live (`go-live.yml`, `review.yml`) was written, not run. Test it on your own repository.
- `gates.md` records a decision; it is not a lock and does not stop a person typing a name they should not. A
  repository admin can change the environment rule.
- The deny rule is a seatbelt: in the recorded probe it matched 1 of 4 spellings. The gate check in
  `pipeline.py go-live` and the protected environment are what held.
- The critic's banned-claims list only catches wording on the list. The owner still reads every line at Gate 1.
- `build_report.py` checks pass wording against counts; it does not judge the page. `verify.py` judges only what
  the data file and the quoted page text can prove; NOT CHECKED items need a person.
- It does not set prices, send anything to a client, or touch a real client site. A real client site needs its own
  access rules and its own testing first.
- Screenshots from the recorded runs are not shipped, so `verify.py` re-run on the fixtures rejects every finding
  ("screenshot file does not exist"). The shipped `verify.json` files are the recorded verifier output.

## Tested

Offline for the kit: `pipeline.py --help`; `build` blocked with gate 1 empty, with one unknown open and with all
unknowns open (0 model calls, nothing in the ledger); `approve merge` refused before send; `go-live` refused with
gate 3 empty and without the release key; `build_report.py` on both sample runs reproduces the recorded reports
(NOT CHECKED listed under "Needs a human look", never counted as pass); `--check` exits 1 on the handcrafted and
the model-written "passed" summaries; `break_tests.py b1-price-row` fails the planted no-row price; all Python
compiles; both workflows parse as YAML; all JSON loads. Stages that call Claude need your Claude login / API key.
